# 沙盘红绿灯识别：同类方案与最佳实践调研

> 调研日期：2026-10-28　｜　范围：SAHI/切片推理、红绿灯两级检测（粗定位+分类）、云台主动视觉、ROS2/小车开源项目状态机、YOLO 小目标训练侧改进
> 说明：文中标「实测」的是被引用方论文/官方文档给出的数字；标「推算」的是用本项目参数（640×480 画幅、灯约 16×25 px、模型输入 320）算出来的；标「未验证」的表示本环境未能取到原始出处或未做复现。

## 0. 先复算一遍我们的现状（后面所有建议都基于这组数字）

| 项目 | 数值 | 说明 |
| --- | --- | --- |
| 画面 | 640×480 JPEG | web_video_server `snapshot?topic=/image_raw` |
| 灯尺寸 | 约 16×25 px | 占画面高 25/480 = **5.2%** |
| 模型输入 | 1×3×320×320，端到端无 NMS，1×300×6 | YOLO26s OpenVINO，出口固定 320 |
| 整帧缩到 320 后灯高 | 25 × 320/480 ≈ **16.7 px**，占输入 5.2% | 仍 < DORI「可检测」10% 线 |
| 单次推理耗时 | 340 ms ÷ 8 ≈ **42 ms/次**（推算） | 8 次 = 7 带 + 整帧 |
| 顶带 45%×30% | 288×144 px | 若要塞满 320×320，纵向要放 2.22×，横向只放 1.11× → **宽高比 2:1 被拉成 1:1**（除非 letterbox） |
| 中部两块 45% | 2 × 288 = 576 px | **640−576 = 64 px（10% 宽）竖条盲区**，若两块紧贴左右排布则中间一定漏 |
| 底部两块 55% | 2 × 352 = 704 px | 重叠 64 px，覆盖没问题 |
| 三行高度合计 | 30%+40%+28% = **98%** | 紧贴排布还剩 9.6 px 未覆盖 |
| DORI 尺度目标 | 「可检测」= 目标高 ≥ 画面 10%，「可识别」= ≥ 20% | 320 输入里即 **≥32 px / ≥64 px**；所以我们至少要让灯在输入里 ≥32 px，最好 48–64 px |
| 需要的放大倍数 | 32/16.7 = **1.9×**，48/16.7 ≈ 2.9× | 即切片高度应 ≈ 480/1.9 … 480/2.9 = **165–250 px**，而不是现在的 144/192/134 px 之外再加非等比拉伸 |

结论：我们的「7 带」本质就是**手工 ROI 切片**（hand-tuned SAHI），方向是对的；问题不在「要不要切」，而在**切块的长宽比、覆盖完整性、合并策略**这三件事没按成熟做法来（见 ③）。

## 1. 结论摘要（6 条，可直接采用/否决）

1. **【采用】保留固定带，但把「带」改成近方形块，并按 DORI 反推尺寸。** SAHI 论文给的是 640×640 切片 + 25% 重叠（VisDrone），supervision 官方默认 320×320 + 0.2 重叠，Ultralytics 官方教程示例 256×256 + 0.2 重叠；这些默认值对 640×480 的整帧只相当于 1.0× 缩放，**对我们这种 16×25 px 的灯没有任何帮助**——有用的是「切片后放大」。按 DORI 10% 线反推：切片高度取 **160–240 px**（放大 2–3×），宽高比接近 1:1（例如 3×3 的 213×160，或 2×3 的 320×160 再 letterbox），灯在输入里能到 **32–48 px**。
2. **【采用】合并换成 SAHI 的默认策略：GREEDYNMM + IOS 匹配 + 阈值 0.5，而不是纯 IoU。** SAHI 源码默认就是 `postprocess_type="GREEDYNMM"`、`postprocess_match_metric="IOS"`、`postprocess_match_threshold=0.5`、`overlap_*=0.2`；supervision 也提示 IOS（交集/较小框）比 IOU 更适合跨切片同一目标（大小不一致时 IOU 会偏低）。我们现在「按 IoU 合并」会在同一盏灯被两个不同尺度切片各抓一次时留下重复框，后续投票计数被污染。
3. **【采用】把颜色判定从「检测头」拆出来做「裁切 + 小分类器/HSV 复核」，这是工业界主流，不是权宜之计。** Autoware 的正式流水线就是 map 粗定位 → YOLOX-s 细检测（`score_thresh=0.3`, `nms_thresh=0.65`）→ 裁切分类。其官方分类器在 **128×128 (EfficientNet-b1) 上 99.76%、224×224 (MobileNet-v2) 上 99.81%**（8.34 万张日系灯图），并且**同一节点保留了 HSV 分类器作为可选后端**；红灯不亮/逆光时直接输出 `UNKNOWN` 而不是硬猜。这正是我们「把灯放大再判色」和「抑制红锥桶」的正统做法。
4. **【采用】判停用「多帧 + 保守仲裁」，判走用「更高门槛」。** Autoware 的 arbiter 规则是**只要两路来源颜色不一致就输出 UNKNOWN**（宁可不走）；Duckietown 的 `stop_line_filter` 用 `off_time: 2`（离开停止线后 2 s 内不再触发）；DonkeyCar 的停止标检测只用一个 `STOP_SIGN_MIN_SCORE = 0.2` 单帧阈值（且官方文档自己承认 SSD 远距离小目标不行）。**红→停可以低门槛（2/3 帧）、绿→走必须高门槛（3/3 帧 + 位置一致）**，因为「误停」的代价远小于「误走」。
5. **【部分否决】纯 SAHI 自动切片替代我们现在的 7 带：否决。** 理由是可验证的：SAHI 的开销随切片数线性增长（论文明确说明），我们已经是 8 次推理 / 340 ms；再改成自动切片（640×480 + 320 片 + 0.2 重叠 = 3×2 = **6 片**，且几乎不放大）只会更慢更差。**要么保持手工 ROI（带几何先验），要么把手动带改成「近方形 + 20% 重叠」的 6–9 块。**
6. **【部分否决】指望「等模型自己学会小目标」：现在别等。** Ultralytics 官方在 issue #6483 里说得很直白：训练分辨率要贴近推理分辨率、切图时**不要把目标切在交界处**、2×2 px 已接近极限；提问者用 1216 输入 + P2 训练 + SAHI 推理才能稳定检出 3×3/3×4 的块。也就是说：**在不重训的前提下，切片放大是唯一有效杠杆；重训的第一优先级是把「小灯样本 + 高分辨率」喂进去，其次才是 P2/imgsz。**

## 3. 针对我们现状的具体建议

### A. 马上能用（只改参数/配置，不动模型、不重训）

**A1. 修掉切片几何的三个硬伤**（先做这个，收益最确定）

| 问题 | 现状（推算） | 改成 | 依据 |
| --- | --- | --- | --- |
| 中部盲区 | 2×45% = 90% 宽 → 中间 **64 px** 竖条无人看 | 中部改 **2×55%**（重叠 64 px），或直接 3 列 × 45% | 覆盖完整性优先；SAHI/Ultralytics 都强调别把目标放在切片外/交界处 |
| 行间无缝 | 30+40+28 = 98%，剩 9.6 px | 行高改 **35% / 40% / 35%**（相邻重叠 10% = 48 px） | SAHI 论文：重叠带来 small/medium AP 提升，25% 是其推荐值上限附近 |
| 非等比拉伸 | 288×144 拉成 320×320（纵横比 2:1→1:1） | **等比缩放 + letterbox**；或直接把块选成近方形（见 A2） | YOLO 对形变有鲁棒性但非无限；非等比会让「灯箱三灯横排」的几何约束失效 |

**A2. 用 DORI 反推带尺寸（把「带的尺寸」变成可计算的量）**

- 目标：灯在模型输入里高 **≥32 px**（DORI 可检测 10%），争取 **48 px**。
- 灯原始 25 px → 需要放大 **1.3×（32px）/ 1.9×（48px）/ 2.6×（64px）**。
- 放大倍数 = 320 ÷ 切片短边（等比缩放到短边=320 时）。反推切片短边 = **320/1.3 … 320/2.6 = 123–246 px**。
- 所以推荐：**每块 213×160（3 列 × 3 行，放大 2.0×，灯约 32×50 px）**，或 **320×213（2 列 × 2 行 + 顶行，放大 1.5×，灯约 24×37 px）**。
- 先跑 A/B：`3×3@213×160` 与 `2×3@320×160` 两套，比较同一段实车视频上的 red 最小分与召回。

**A3. 合并策略换 SAHI 默认**

- `match_metric = IOS`（不是 IOU）、`match_threshold = 0.5`、`match_type = GREEDY`（SAHI 的 `GREEDYNMM`）。
- 同一灯被两块命中时**保留「放大倍数更大 + 分数更高」的那个框**（SAHI 是贪心 NMS，按分数；我们可以按 分数×(1+0.1×scale) 排序，把大尺度优先）。
- 阈值：先按 Autoware 的 `score_thresh = 0.3` 收候选，**最终判红用 0.5**；我们现在最差 0.43 的那一档应该落在「候选」而不是「判定」里。

**A4. 红/绿分开设门槛 + N-of-M 投票（这是压误检最便宜的一招）**

| 判定 | 建议参数 | 理由 |
| --- | --- | --- |
| 红灯（触发停车） | **2/3 帧**命中，单帧 score ≥ **0.45**，框中心落在画面上半部（y < 0.6H），面积 **400–4000 px²** | 误停代价小；低门槛保召回 |
| 红灯（维持停车） | 允许 1 帧丢失；**连续 5 帧（≈1.7 s）无红**才转「无灯」 | 3 fps 下 5 帧≈1.7 s，接近 Duckietown 的 `off_time: 2 s` |
| 绿灯（触发通行） | **3/3 帧**命中，score ≥ **0.6**，且三帧框中心抖动 < **20 px** | 闯红灯代价大；位置一致性能压掉「红锥桶/红屋顶」这种偶发高分 |
| 无灯（触发通行） | 连续 **4 帧**（≈1.3 s）red 与 green 都 < 0.3 | 业务口径是「无灯也走」，必须有明确的「确实没灯」路径 |
| 灯色未知 | 两路判定冲突（YOLO 说 red、HSV 说非红）→ **UNKNOWN**，按 red 处理（保守） | Autoware arbiter：不一致即 UNKNOWN |

**A5. 给红色误检加三道几何/光度闸门（几乎零成本）**

1. **尺寸上限**：沙盘灯 16–25 px（放大后 32–50 px），红锥桶放大后通常 **> 60 px** 且更「立」——用 `h/w` 比：灯箱/圆灯 **0.5 ≤ h/w ≤ 1.2**；锥桶 **h/w > 1.3**，直接丢。
2. **自发光判据**：取框内中心 50% 区域，`V ≥ 200 且 S ≥ 150` 的像素占比 ≥ **30%** 才算红灯（漫反射的红漆亮度低）。阈值需现场用 20 张正样本 + 20 张锥桶/红屋顶负样本标一次（Autoware 的 HSV 后端就是这套 min/max 参数化）。
3. **三灯结构约束**：同一 ROI 内若检测到红，且其右侧 1–3 倍框宽处存在另一盏灯（任意颜色）→ 置信度 +0.1；孤立红块不加分。这条对「多路口 99 盏灯」的冗余场景特别有效，也是「灯箱」相对「红锥桶」的本质差异。

**A6. 云台动作与投票对齐（把 340 ms/帧 算进时序）**

- 3 fps 下：pitch 1450 压下后**至少等 2 帧（≈700 ms）**再取斑马线确认，避免拍到云台运动模糊帧。
- 抬头到 1720 后同样等 2 帧再开始红灯投票。
- 停车等待期间把推理频率降到 **1 Hz**（每 1 s 一次）省 CPU；绿灯可能随时变，1 s 采样对「红灯剩余时长」足够（沙盘配时通常 > 10 s，**未验证**）。

**A7. 把「斑马线」当停止线的先验（我们模型本来就有 `crosswalk` 类）**

- Autoware 用 HD 地图回答「现在是哪一盏灯」，我们用不了地图，但可以用 **crosswalk 框的底边在画面中的 y** 当停止线距离代理：`crosswalk` 框底边 y > 0.75H（即在车头附近）→ 已到停止线。
- 好处：不再只依赖「红灯框面积变大」这种尺度判据；且 `park/go/right` 类可以顺带确认「这是在路口，不是在路边看到一块红」。

### B. 需要改代码（小重构，1–2 天）

**B1. 把「检测」拆成两级，形状对齐 Autoware**

```
整帧(1 次推理, 320 全图)  →  只当"哪里可能有灯"的粗筛（低门槛 0.2）
        ↓
候选框外扩 1.5–2.0 倍（对应 Autoware 的 ±1° / ±0.5 m 标定余量）
        ↓
裁切 → 等比缩放到 320 → 推理（此处可只跑 1–2 个裁切，而不是 7 个）
        ↓
判色：YOLO red/green 分数 + HSV 复核 + h/w 与自发光闸门
        ↓
N-of-M 投票 → 状态机
```

- 每次循环推理次数从 **8 降到 2–3**（整帧 + 1–2 个裁切），按 42 ms/次估算 → **~130 ms/帧（7–8 fps）**，比现在的 340 ms 好 2.5 倍以上。
- 只有当整帧粗筛无候选（开阔路段）时才回退到「固定 5–6 带扫描」，用于「远距离早期发现红灯」。
- 这其实就是 Autoware 的 `map_based_detector → fine_detector → classifier`，只是把「地图」换成「整帧粗筛 + 车道路锥」。

**B2. 让 OpenVINO 并发起来**

- 现在 8 次推理是串行 42 ms × 8。OpenVINO 的 `AsyncInferQueue` / 多 `InferRequest`（`ov::hint::num_requests`）在 CPU 上通常能把吞吐提到 1.5–2×（**未在我们机器验证**，需实测）。
- 若改用 B1 的两级方案，串行也已够用，可不做这项。

**B3. 状态机（建议直接照这个写，参数见 A4）**

```
CRUISE ──红灯 2/3 帧──▶ STOP_CONFIRM（pitch 1450，等 2 帧）
STOP_CONFIRM ──crosswalk 命中 或 红灯高置信──▶ WAIT_RED（pitch 1720，1 Hz 采样）
STOP_CONFIRM ──无 crosswalk 且红灯消失──▶ CRUISE（回到 1720）
WAIT_RED ──green 3/3 + 位置一致──▶ GO
WAIT_RED ──连续 5 帧无红无绿──▶ GO（无灯路口）
WAIT_RED ──连续 5 帧 UNKNOWN──▶ 保持停车 + 告警（人接管）
GO ──起步后 2 s 内屏蔽 red 触发──▶ CRUISE   # Duckietown off_time 类比
```

- 关键点：`UNKNOWN` 是**一等的状态**，不要降级成「无灯」（Autoware 对逆光/ROI 为空就是返回 UNKNOWN；DonkeyCar 那种 0.2 阈值直接停车在真实场景很容易被一块红物反复逼停）。

**B4. 增加「离线回放 + 打分」脚本（可测性）**

- 把实车录的 JPEG 序列 + 人工标注（每帧是否有 red/green、框）存到 `.work/`，跑一次得到：召回、误报/分钟、最差分、每帧耗时。
- 只有在有这张表的前提下，A2/A3/A4 的参数才有意义；否则每次调参都是凭感觉。这是当前最缺的东西。

### C. 需要重新训练（如果 A/B 之后仍不够）

| 优先级 | 做法 | 参数 | 预期 |
| --- | --- | --- | --- |
| 1 | **切片式微调（SAHI 的 SF）**：训练时把原图随机切成 480–640 的 patch（我们按 160–320 更贴近推理分布），**原图也保留** 20–30% 以维持大目标 | 每 epoch 随机 patch 尺寸；lr 参考论文 SGD 0.01 / momentum 0.9 / wd 1e-4 / warmup 500 iter | 论文里小目标 AP50 +13.6（TOOD），是单项收益最大的一招 |
| 2 | **提高训练分辨率到 640，推理也用 640** | Ultralytics 官方建议「训练分辨率贴近推理分辨率」；issue #6483 实测 1216 优于 320-tiled | 直接消除「整帧缩到 320」的信息损失；代价是 OpenVINO 上 640 比 320 慢约 3–4×（**未验证**） |
| 3 | **加 P2 检测头** | `yolov8-p2.yaml` 一类配置（P2 在 stride 4 上出检测）；官方提醒要重调 anchor | stride 8→4 对小目标通常有正收益；二手来源称 "yolov8-p2.yaml 精度优于默认"（**未验证**，建议自己 A/B） |
| 4 | **补小目标正样本 + 负样本** | 每帧 16–25 px 的灯至少 **2000–3000 个实例**；红锥桶/红屋顶/红标志各 ≥300 张负样本（可只标 `background` 或新增 `red-object` 类） | 类别不均衡 + 难负样本是「分数对位置敏感」的根因之一 |
| 5 | **合成数据**（沙盘可控，性价比高） | 把红灯/绿灯贴图按透视贴到沙盘背景，专补「小、远、偏、暗」四种 | 论文：mAP 与 F1 各比真实数据参考模型高近 4 个百分点；还能补黄灯这类长尾（我们不做黄灯，但可以做「非红非绿的干扰灯」） |
| 6 | **别只信 320 的蒸馏模型** | 若必须保留 320 输入，则推理端只能靠切片（A2）；两者二选一 | — |

> 注：`yolov8-p2.yaml` 在本环境未能直接抓取原文核实（GitHub raw 抓取失败），二手来源（MDPI *AgriEngineering* 7(1):2 文中提到 yolov8x + `yolov8-p2.yaml` 精度/召回更优）**未验证**，实施前请以 `ultralytics/cfg/models/v8/` 目录是否存在该 yaml 为准。
