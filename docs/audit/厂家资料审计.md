## 0. 结论（先看这一段）

1. **厂家确实自带一套「已知路网导航」实现**，形状与用户目标 3 几乎一致：预先在 `road_network.yaml` 里定义节点（含 x,y,yaw）与有向邻接表 `to`，车端 `road_network_navigator` 用 **BFS** 求节点序列，再按 **0.05 m 线性插值**成密集 `nav_msgs/Path`，通过 **FollowPath action** 直接交给 Nav2 控制器执行（**不经过全局 planner / bt_navigator**）。这套东西可以直接作为我们目标的实现蓝本，甚至可直接调用。
2. **最大的功能缺口正是用户说的「选起点」**：厂家只暴露「选目标」——`road_network_ui.py` 发 `Int32 /request_waypoint`；起点是隐式的（`current_index`＝上次到达节点，或 TF `map←base_link` 投影最近边）。**没有任何"选起点"接口、没有起终点对、没有路网拓扑编辑的电脑端入口**。
3. **规划质量上的缺口**：BFS 求的是**最少跳数**而非最短米数；边是直线段，**不查代价地图/不避静态障碍**（只有执行层 RPP 控制器的局部碰撞检测兜底）；节点 16 被硬编码为红绿灯点。这些是我们要改造的重点。
4. **建图/定位链路是标准的 slam_toolbox + Nav2(AMCL)**：地图存 `/home/ubuntu/ros2_ws/src/slam/maps/<map>.yaml+.pgm`，路网 yaml 存 `/home/ubuntu/ros2_ws/src/road_network/config/*.yaml`，路径全部硬编码（可预期、也可被我们覆盖）。
5. **红绿灯与导航的耦合很浅**：仅「距写死节点 16 < 1.5 m 且 YOLO 红框面积 > 2300 → 急停，绿 → 断点续跑」。识别侧模型与类别（`best_traffic_26`：go/right/park/red/green/crosswalk）与我们仓里已有的完全同源，**没有额外可挖的识别算法**，价值在"停车判据与恢复策略"的参考值。

### 3.2 路网文件格式（`src/road_network/config/*.yaml`）

```yaml
waypoints:
  - id: 0
    pose: [0.0, 0.0, 0.0]      # x, y, yaw（yaw 可省略，省略时用行进方向）
    to: [1, 2, 4, 5]           # 有向邻接：只写这一侧就只允许单向
  - id: 16
    pose: [0.4, 1.30]
    to: [3, 2]
```

- `to` 是**有向**的，双向必须写两次（示例里多数都写了双向）。
- 现成路网：`road_network.yaml`（9 节点）、`self_driving_network.yaml`（17 节点，带中文地标注释：`#仓库 / #工地 / #红绿灯 / #商店`）、`road_network_{community,factory,logistics}.yaml`。
- 单位米；`self_driving_network.yaml` 里注释 `# yaw 0.0 前 1.57 左 3.14 后 -1.57 右`。

### 3.6 风险/不一致（实车要确认）

- `nav2_execution_node` 用的 action 名是**全局** `'follow_path'`，而 controller_server 被 `PushRosNamespace(robot_name)` 包住；若 `HOST` 非空，`/follow_path` 与 `/<HOST>/follow_path` 不匹配。厂家演示应是在 `HOST` 为空时跑通。我们自己实现时**不要依赖命名空间**。
- navigator 的 `base_frame_id = 'base_link'`，Nav2 侧是 `base_footprint`，两者取 TF 时要留意。
- `road_network_ui.py` 与 builder 硬编码 `config/road_network.yaml`、`MAP_DIR`，不支持任意文件名（launch 支持 `file_name` 参数，UI 不支持）。
- 路网导航也把 `planner_server` 拉起来了，但 Path 由 BFS 直出；`waypoint_follower` 同样被启动但没人用。

### 9.3 仓库里缺失（必须我们自己补）

1. **路网数据模型与校验**（节点/有向边/红绿灯标记/单位与越界检查）——我们仓里没有任何图结构代码。
2. **起→终规划与执行链**（生成路径 → 交给 Nav2 → 到达/失败/取消状态机），以及"先到起点再出发"的两段式流程。
3. **路网编辑/导入 UI**（Tk 画布上点选节点、连线、改 id、拖拽微调、保存 yaml/json）。
4. **路网与代价地图的一致性检查**（厂家完全没做：边穿墙、边上障碍物、地图/路网坐标系不一致 —— 我们可以用 costmap 校验并在 UI 上标红）。
5. **多点任务/巡检**（顺序 waypoint、每点停留时间、循环）——厂家有 `nav2_waypoint_follower` 但路网模式不用。
6. **红绿灯的空间约束**（按 x,y 半径触发而不是写死节点 id；地图级红绿灯位置配置）。
7. **OpenVINO 模型导出/替换流程**（课程缺此步；我们已有 `app/models/traffic_light`，需要把"换模型/换类别"流程文档化）。
