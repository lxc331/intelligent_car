## 结论摘要

1. 导航链的 PC 侧编排比交接文档更完整：地图导入→归一化→上传、AMCL 初值、Nav2 action、2 秒运动租约、任一许可失效即取消，都有明确实现与离线测试。
2. **Nav2 action 不在 rosbridge 上**：PC 只发一条 SSH 命令到车端临时 `runtime.py`，由它起 rclpy 节点调用 `/compute_path_to_pose`、`/navigate_to_pose`。rosbridge 客户端本身只有 publish/subscribe/call_service，没有 action 通道。
3. 与用户目标「已知路网 + 选起点终点」的差距**不在通信层，在数据模型层**：没有路网拓扑、waypoint、任务队列；终点是地图上的自由点，起点永远是当前定位位姿。
4. 红绿灯是「新马线路口」场景驱动：**红灯判定被斑马线确认门控**（`app/carapp/core/traffic_scene.py:80`），斑马线漏检 = 不减速也不停车 = 闯红灯。这是当前红绿灯最大的功能缺口。
5. 实车最大阻塞不是代码 bug，而是**车端环境假设从未验证**（14 个节点名、`/home/ubuntu/ros2_ws/src/navigation/config` 配置路径、`/scan_raw`+`/odom` 必须有 publisher），其次是导航期间 **4.5 次/秒 SSH + python3 冷启动**的轮询开销。

## 1.6 结论：要支持「已知路网 + 选起点终点」现在缺什么

按依赖顺序，**缺失全在数据模型与任务层，通信与执行层基本够用**：

1. **没有路网/waypoint 概念**。全仓 grep `waypoint|路点|路线|多点|巡检` 0 命中；地图模型只有栅格 + 位姿（`model/map_data.py` 的 accept_map/accept_map_pose），没有节点、边、单行、路口元数据。→ 需要新增 `map_routes`（节点坐标+邻接+可选方向约束）并随地图保存。
2. **没有「选起点」**。起点隐含为当前 AMCL 位姿：`runtime.py:435` `goal.use_start = False`，规划从实时位姿出发。→ 要么提供「起点=地图上任一点 → 先下发 initialpose 再规划」（可行性低，AMCL 会重新收敛），要么提供**离线路径推演**：只调 `ComputePathToPose` 并传 `use_start=true` + start PoseStamped，不驱动车。
3. **没有多点/顺序导航**。有 `goal_handle` 时新 plan/navigate 直接被拒（`_request` 的「请先等待当前导航结束或取消」），PC 也只保存单个 `self.goal`。→ 需任务队列 + 逐段确认到点。
4. **到点判定只信 Nav2 succeeded**：没有到点容差、停留时间、到点动作（转向/拍照/继续），也没有「已到达第 N 段」的 UI。
5. **没有全局重规划入口**：中途只能 `stop_all`（取消），没有「换一条路/跳过当前段」；重规划完全由 Nav2 行为树内部完成。
6. **没有路线持久化与回放**：成功一次的目标点不落盘（`settings.json` 只有 `navigation.speed`），下次还要手点。

## 2.2 状态机（新马线路口确认 → 减速 → 红灯停 → 恢复）与关键阈值

- 三处阈值必须同时看（单位：源图像素按 640×480 归一）：
  `app/carapp/core/traffic_light.py:8-10` `FRAME_TIMEOUT = 1.2` / `CLEAR_SECONDS = .8` / `CLEAR_FRAMES = 3`
  `app/carapp/core/traffic_scene.py:22-24` `SLOW_SPEED = .1` / `PASS_SECONDS = .4 / SLOW_SPEED`（=4.0 秒）/ `FRAME_TIMEOUT = 1.2`
  `app/carapp/core/traffic_light_detector.py:151-152` 红灯必须在正前方带：`.15 < (x1+x2)/2/width < .85 and .02 < (y1+y2)/2/height < .80`
- 流程（`TrafficScenePolicy.observe`）：
  1) 取 crosswalk/red/park/right/go 框，横向必须在 15%–85%（`traffic_scene.py:58`）；
  2) **斑马线确认**：`crosswalk_y = cy*480`，`if self.confirmed >= 3:` → `self.active, self.remaining = True, self.PASS_SECONDS`（`:76-78`）；
  3) 减速：`snapshot()` 里 `slowing = self.active or self.early_park` → `speed_limit = SLOW_SPEED = .1`（`:98,104`）；
  4) 红灯：`red = self.active and (red_area > 700. or self.red_latched and red_area > 0.)`（`:80`）——**只在路口内才认红灯**；
  5) 停车与保持：`TrafficLightPolicy.observe` 红灯 → `blocked=True`；清除需要 3 个不重复帧且 ≥0.8s（`traffic_light.py:41`），画面超时/异常一律 `blocked=True`：
  `app/carapp/core/traffic_light.py:52-57`（`stale = age is None or age > self.FRAME_TIMEOUT`）；原因文案含 `"未开启"/"等待画面，停车"/"画面超时，停车"/"识别异常，停车"/"红灯停车"`
  6) 恢复：`clean` 后 `blocked=False`，导航侧由 runtime 自动恢复（见 2.3），人工侧下一条指令即生效。
- 顶部开关默认**关闭且不持久化**：`app/carapp/config.py` 与 `settings.json` 均无 traffic 键（grep 0 命中），按钮文案 `app/carapp/ui/topbar.py:115` `text="红绿灯功能：关闭"`；每次启动都要手点开（`TrafficLightPolicy` 默认 `enabled=False`）。

## 2.3 与底盘控制的耦合点（是否被运动占用检查拦住）

三条运动路径都存在，且处理方式不同：

1. **PC 侧手动/跟踪/巡航**：统一走 `AppContext.publish_twist`，被交通场景 guard 包住（不是用 `motion_in_use` 拦，而是替换指令）：
   `app/carapp/features/base.py:127-133`
   `control = getattr(self.app, "traffic_light", None)` / `scene_guard(vx, vy, wz, lambda x, y, z: publish(command=(x, y, z)))`
   `app/carapp/core/traffic_light.py:150-155` `values = (0., 0., 0.) if state["blocked"] else limit_twist(vx, vy, wz, state["speed_limit"])`
   巡航还额外自己查一次互锁：`app/carapp/core/cruise.py:137` 与 `:141` `decision = (0.,0.,"红绿灯暂停，连续未见红灯后自动继续",False)`。
2. **车端 Nav2**：PC 通过心跳把 `paused/traffic_enabled/traffic_speed_limit` 写进租约（`navigation_remote.py:115-123`），runtime 拿不到或读到异常时**失败即停**（`navigation_remote.py:127-128` `paused=True, pause_reason='红绿灯控制状态读取失败'`），并在车端解除 Nav2 goal、零速、等红灯消失后**重新规划恢复**：
   `app/carapp/core/navigation_runtime.py:244` `def _pause_for_traffic(self):`
   `app/carapp/core/navigation_runtime.py:261` `def _resume_after_traffic(self, now):`（内部 `internal_resume=True`，不重复回 RPC 应答）
3. **运动占用检查**：红绿灯**不占用底盘**（不设 `motion_active`），所以不会挡住别的页面；反过来导航/巡航启动时的 `motion_in_use()` 也不会因为红绿灯而失败。只有导航心跳的 `paused` 会让 runtime 不驱动。
   → 注意：这是 PC 侧互锁，**只在指令经过 PC 时有效**；若有人直接在车端用键盘/手柄/其他节点发 `/controller/cmd_vel`，红绿灯完全管不到。

## 2.4 离线测试覆盖到哪一层

- `test_traffic_light.py` 22 例：三帧/0.8s 清除、超时保持、旧帧/未来帧/重复帧不能清红、解码失败保持、看门狗独立停、关闭即不限制、锁内发布不被红灯超越。
- `test_traffic_scene.py` 11 例：`test_red_outside_confirmed_crosswalk_does_not_trigger`（确认了 2.2 的门控行为）、分辨率归一、红灯等待不使 PASS 过期、相机断流重置路口。
- `test_traffic_light_detector.py` 16 例：letterbox/坐标还原、输入格式、软/真冲突回退（**无颜色兜底**：`test_inference_failure_propagates_without_colour_fallback`）、真实 OpenVINO 冒烟（本机执行，openvino 2026.4.1）。
- `test_traffic_navigation.py` 14 例：心跳互锁、暂停不撤租约、恢复等 cancel 完成、停车/断流/新 epoch 不可恢复。
- **未覆盖**：真车相机视角/曝光/夜间、真车 6fps 有效帧率、CPU 争用（车身同时跑 Nav2）下的延迟。→ 需要实车采集视频做离线回放（目前无录带标注的路口数据）。

## 2.5 真实路面漏检/误检会怎样降级

- **红灯漏检（模型没给出 red 框）**：`blocked` 保持 False，3 帧后恢复通行 → **不减速直接过路口**。减速本身也依赖 crosswalk 确认（`traffic_scene.py:98`），所以「红灯 + 斑马线没检出」= 全速闯红灯。这是最需要优先改的行为。
- **红灯误检（远处/侧方红灯被端上正前方带）**：x 15%–85%、y 2%–80% 的窗口很宽，相邻车道红灯可能进入；`red_latched` 会把「已变绿灯但残留红框」继续压住（`:80,82`），靠 0.8s/3 帧清除。
- **画面断流/模型异常**：一律 `blocked=True` 并每 0.2s 补发零速（`traffic_light.py:183-185`），是 fail-safe；但**开关打开且相机没接时车会一直不动**（用户视角像"死机"），文案只有「等待画面，停车」。
- **行人/横穿**：模型只做红绿灯，不检行人；低速 0.1 m/s 与 Nav2 障碍层是唯一保护。
