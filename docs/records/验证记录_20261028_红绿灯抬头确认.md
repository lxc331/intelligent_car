# 验证记录：红绿灯「抬头确认」+ 放大检测（2026-10-28）

## 1. 结论

红绿灯识别在实车上已经跑通「接近 → 确认斑马线 → 自动抬头 → 确认红灯 → 停车」这条链路：
实车连续 40 帧回放中，斑马线第 2 帧确认后立即仰起云台，第 6 帧开始红灯面积稳定
506–552 px²（>450 门限），第 7 帧进入红灯停车状态并持续 21 帧；8 秒后按设计回前视
0.8 秒再抬头复核。离线单测 63 例、全量 41 个测试模块全部通过。

## 2. 需求与业务口径

- 用户（m00680 答复）：先加放大检测（裁切放大推理），红灯面积门可配置；担心把其它红色
  物体误判成红灯；业务上「检测到斑马线后抬头确认红绿灯，红灯就在斑马线处停下，否则直接走」，
  当前不做黄灯。
- 用户（m01133）：小车会停在正确的停车位（斑马线前），沙盘不大；可以用调转摄像头确认车与
  斑马线的相对位置；沙盘里有 99 个红绿灯，判定要留冗余；先把眼下这个做完。

## 4. 行为约定

| 配置键 | 默认 | 含义 |
| --- | --- | --- |
| `traffic_light.zoom` | 顶部 3 块 45%×30%（y 0–30%）+ 中部 2 块 45%×40%（y 28%–68%）+ 下方 2 块 55%×28%（y 72%–100%） | 放大推理区域，按离路口远近分三条带 |
| `traffic_light.zoom_confidence` | 0.35 | 放大区域专用置信度 |
| `traffic_light.red_area` | 450 px² | 红灯停车面积门限（640×480 折算） |
| `traffic_light.red_frames` / `red_hold` | 2 / 0.6 s | 连续 2 帧确认、漏检保持 0.6 s |
| `traffic_light.confirm_pitch` | 1720 | 停车前抬头角度 |
| `traffic_light.restore_pitch` | 1500 | 复位到前视角度 |
| `traffic_light.confirm_delay` | 1.4 s | 斑马线消失多久后复位 |
| `traffic_light.confirm_hold` | 8 s | 仰视最长保持时间，超时回前视 |
| `traffic_light.confirm_retry` | 0.8 s | 回前视后多久再次抬头复核 |

规则：只有场景确认斑马线（`crosswalk_active`）才抬头；抬头只改视角，不改变停车判定；
红灯确认只在「斑马线已确认」前提下生效（沿用 `core/traffic_scene.py` 的 `active` 门控，
这样路侧红色物体不会单独触发停车）；关功能、切车、退出都会立刻复位云台。

补充（同日修正）：最初实现在仰视满 `confirm_hold` 后无条件回前视，而回前视后红灯从画面消失，
`traffic_scene` 的 0.8 秒清灯逻辑会把停车释放掉——红灯还亮着却放行。现在改成**红灯可见期间
不切回前视**，只有红灯消失（或始终没确认到红灯）且仰视已满 `confirm_hold` 才回前视，
分别提示「红灯结束，云台复位」和「路口等待超时」。`test_traffic_light_look.py` 相应改为
两例（长红灯保持仰视、红灯消失后复位并按 retry 重新抬头）。

## 5. 验证证据

1. 单元测试：`tests.test_traffic_light_look` + `test_traffic_light` + `test_traffic_scene`
   + `test_traffic_light_detector` + `test_traffic_light_ui` 共 **63 例 OK**。
2. 全量回归：`.work/run_tests_per_module.py` → **modules=41 ok=41 bad=0**。
3. 实车时序（`.work/live_traffic_light_flow.py 40`，车停在斑马线前、云台前视）：

   ```
   0-1  确认斑马线 1/3、2/3
   2    路口抬头确认红绿灯，云台仰视 1720         active=True
   6    红灯面积 529 px²
   7    红灯确认，斑马线前停车；red=True          持续到第 27 帧
   26   路口等待超时，云台复位 1500
   ```

   单帧耗时 156–219 ms（全帧 + 4 块放大共 5 次推理），App 限 6 fps 会自动丢帧取最新帧。
4. 几何依据（同一停车位）：前视 pitch 1450 时斑马线中心 y=438（>300 满足门控），但画面里
   看不到灯；抬头 pitch 1680/1720/1760 时下方放大块红灯分数 0.68/0.73/0.78、面积约 528 px²。
5. 车与斑马线相对位置的确认方式：pitch 1450 画面里最近斑马线贴在画面下沿（y 396–480），
   说明车头已到停止线前。
6. 七块放大区域的离线矩阵（10 张实车帧，生产阈值 conf 0.5 / zoom_conf 0.35）：

   | 区域组合 | 每帧最强红灯分数 | 最差帧 |
   | --- | --- | --- |
   | 只有中部两块（旧配置） | 0.12 / 0.00 / 0.77 / 0.68 / 0.73 / 0.78 等 | **0.00** |
   | 中部 + 下方（4 块旧默认） | 0.56 / 0.43 / 0.43 / 0.70 / 0.50 / 0.69 / 0.74 / 0.68 / 0.37 / 0.73 | 0.37 |

   单次推理约 30 ms，七块全开一帧 8 次推理约 340 ms（后台线程只取最新帧，实际 3–5 fps）。

## 7. 仍未做 / 风险

- **模型对取景敏感**：同一盏灯在「灯体完整、约 25×25 px、位于画面 28%–68% 高度」时稳定
  0.5–0.87，换到画面顶部或只剩横向灯箱一角时分数掉到 0.05 以下甚至完全不出框。抬头确认
  就是把这个位姿固定下来；沙盘有 99 个灯，换路口后仍需确认新位置的取景。
- 抬头期间前视被遮挡约 8 秒，靠 `confirm_retry` 回前视 0.8 秒；若后续要跑更长的红灯等待，
  需要把这个循环做成可配置的「看灯/看路」占空比。
- 车端只用本 App 的舵机通路，未与人工操作互斥；手动按云台键会和自动抬头抢控制权。
- 真实停车动作还没让小车自己走完（本轮只验证识别与停车指令链路，未在车里点「开始导航/遥控」）。
