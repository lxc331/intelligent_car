# 2 号车参数改用 1 号车实机值（2026-10-31）

## 1. 结论

今天在车旁通过网线确认：这台车的 CPU 序列号是 `e92c53fa0857935d`，末 8 位 `A0857935`，
即 **2 号车 HW-A0857935**。但它昨天（2026-10-30）用 **1 号车档案 HW-10CCA58E 的实机参数**
完成了视觉准备、两爪间标定和追踪夹取。因此把 1 号车那套实测值照搬到 2 号车档案：

- `CALIBRATIONS["HW-A0857935"]`：云台限位 pitch 1150–2250、arm 1200–2000；
  动作 look_down 1300 / look_forward 1500 / arm_up 1200 / arm_down 1700；
  `signs {"pitch": 1, "yaw": 1}`；红绿灯视角 1450 / 1720 / 1500；junction speed_scale 1.87。
- `settings.json`：`tracking_pick.preparation_poses` 增加 `HW-A0857935: {"arm": 1796}`；
  把 10-30 20:36 那次成功标定复制成 `HW-A0857935:red`（x 0.4654 / y 0.8355 / width 0.2891）。
- `car.profile_id = HW-A0857935`、`host = 192.168.150.2`、`transport = wired`。

## 2. 为什么原来的「2 号车实测值」不可信

`docs/records/验证记录_20261028_逐车标定.md` 记录 2 号车「数值越大摄像头越低、俯仰 -1、
物理上限 1800、look_down 1600、arm_down 1950」，但那批数据是**通过无线连接**测的；
用户 2026-10-31 确认：当时很可能把车号搞混了（另一台小车故障期间一直在用这台车）。
同一份文档的 1 号车参数（1300 / 1700 / +1）反而在**这台物理 2 号车上**反复验证通过：

| 时间 | 证据 |
|---|---|
| 10-30 20:36–20:44 | 1 号车档案 + 标定 y 0.8355 → 成功夹起（`app/捕获/追踪夹取/20261030_204405`，阶段_13 可见红块被夹起） |
| 10-31 16:44 | 1 号车档案 → 视觉准备下发 1300/1500/1796，两爪间标定 y 0.7906 成功 |
| 10-31 16:45 | 1 号车档案 → 到达 y 0.801 / 0.840 合爪（夹空是横向对准问题，与舵机方向无关） |

另：序列号通过 `/proc/device-tree/serial-number` 读取，SSH 走网线 `192.168.150.2`（pi）。
