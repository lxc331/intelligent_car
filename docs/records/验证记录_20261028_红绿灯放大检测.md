# 验证记录：红绿灯放大检测 + 可配置红灯判据（2026-10-28）

状态：离线验证完成；实车端到端在车摆回已知位置后复测（见文末“待复测”）。

## 1. 为什么改

实车画面里红绿灯确实在画面中（`pitch=1600` 抬头后红灯点亮、右侧绿灯点亮），但 App 开着红绿灯功能仍不识别：

- 全帧检测（640×480 缩到 320）：只有 crosswalk，**red/green 连 0.05 分都没有**。
- 把红灯所在带裁切放大再推理：×2 时 red 0.620 / 面积 960 px²，×3 时 0.635 / 2205 px²，×4 时 0.607 / 3965 px²。
- 结论：不是阈值、不是门控，是**灯在画面里太小**（原生约 16×15 px，缩到 320 后约 8×8 px）。

## 3. 行为约定

- 放大区域与全帧结果合并后，仍要求红灯**框中心**落在画面横向 15%–85%、纵向 2%–80% 才参与停车判断。
- 红灯停车仍需先满足原有斑马线路口条件（`crosswalk_y > 300` 连续 3 帧），符合用户口径「确认斑马线后再判定红灯，红灯停、否则走，不做黄灯」。
- 放大区域用 0.35 置信度，全帧仍用 0.5；两块区域各占 55% 宽、重叠 10%。
- 默认 `red_frames=2`、`red_hold=0.6`：第一次看到红灯先不停车，第二帧确认后停车；之后短暂漏检 0.6 s 内不松刹车。
- 关闭红绿灯开关、切车、重连摄像头、画面超时仍按原逻辑清空全部状态。

## 4. 验证证据

- 离线测试：`tests.test_traffic_light_detector`、`tests.test_traffic_scene`、`tests.test_traffic_light`、`tests.test_traffic_light_ui` 共 **58 项 OK**。
- 全量回归：`.work\run_tests_per_module.py` → **modules=40 ok=40 bad=0**（`test_vendor_lidar_parity`、`test_integrated_terminal` 各跳过 1 例，原本即跳过）。
- 单帧分块对照（同一张 640×480 实车帧，置信度 0.05 只用于观察原始分）：

| 放大区域方案 | red 分数 | 框/面积 |
| --- | --- | --- |
| 50/50 无重叠（两块 320×288） | 0.082 | 9×30，270 px²（灯被分界线切一半） |
| 55% 宽 + 10% 重叠（采用） | 0.592 | 28×28，784 px² |
| 3 块 40% 宽重叠 | 未检出 red（green 0.865） | — |
| 4 块 30% 宽 | 0.304 | 29×29 |
| 只放大横向通带 y 0.15–0.55 | 0.053 | 25×26 |

- 连续帧：采用 55%/10% 重叠 + 0.5 阈值时 15 帧里 9 帧检出红灯，面积为 784 px²（>700 门限），斑马线确认后 `required=True`；红灯分数在 0.40–0.64 抖动，故按用户选择把放大区域阈值降到 0.35 并加两帧确认。
- 推理耗时：单帧全帧 + 两块约 190–260 ms（含抓帧），App 上限 6 FPS 仍有裕量。

## 6. 待复测 / 已知风险

- 降低阈值后尚未在“车-灯摆回已知位置”的稳定画面下复测；曾出现一次 0/15：当时人手臂进入画面、角度变化后同一盏红灯被模型判成 `crosswalk 0.41`（框 72×22），说明**模型对灯的朝向/距离敏感**，不是阈值能完全覆盖的。
- 误判风险：用户担心其他红色物体被判成红灯。当前缓解是「先确认斑马线 + 面积门 + 两帧确认」，仍建议实车把红色道具放进画面测一次。
- 放大区域固定覆盖画面上方 60%、水平全覆盖；若实车红灯会偏到画面最边缘，需要按实际视角再调 `traffic_light.zoom`。
